# 我把默认的 `code .` 换成了 `zed .`

本期唠嗑。

我已经把默认的 `code .` 换成了 `zed .`。

说来话长。

从我接触编程开始，除了最早学 C 语言的时候用过 Dev-C++，后面无论是前端、Node、Python，还是 Go、Rust，我基本一直都在用 VS Code。

中间当然也试过别的 IDE，比如 GoLand、PyCharm。客观来说，它们确实强，尤其是在对应语言生态里，很多功能做得很完整。但我总是用了几天就切回 VS Code。

原因也简单：笨重，且不习惯。

VS Code 对我来说一直是一个很舒服的平衡点：轻量、快捷、生态好。它不像传统 IDE 那样一上来就给你一整套巨大的工程体系，更像是一个文本编辑器，再加上一套成熟到离谱的插件系统。

你写前端，它可以。

你写 Node，它可以。

你写 Python，它可以。

你写 Go、Rust，它也可以。

所以在相当长的一段时间里，我其实都是 VS Code 粉。不是信仰粉，而是很实用主义地觉得：它确实好用。

## 直到 AI IDE 开始多起来

最近这大半年，我陆续接触了不少 AI IDE。

比如 Cursor、Windsurf、Trae 之类。

它们的方向当然是对的。现在我也很难回到完全没有 AI 辅助的开发状态了。无论是 Copilot、Claude Code、Codex，还是别的 agent，本质上都已经改变了我写代码的方式。

但问题在于：很多所谓的 AI IDE，用起来总让我觉得有点拧巴。

懂的都懂。

很多产品本质上还是 VS Code 的形态，只是在上面叠了自己的 agent 系统。界面像 VS Code，插件生态像 VS Code，操作习惯像 VS Code，然后再加一个自己的 agent window、chat panel、sidebar、任务系统。

这不是说它们没技术含量。

恰恰相反，真正复杂的地方就在这里：在 VS Code 这套编辑器形态之上，又叠了一个完整的 agent orchestration layer。

这个东西可不是放一个聊天框那么简单。

一个真正可用的 coding agent，需要代码库索引、语义搜索、上下文管理、文件读写、diff apply、终端执行、checkpoint、任务队列、工具调用状态、MCP 或外部工具接入，还要有一整套持续流式更新的 UI。

这些东西一旦都塞进编辑器里，所谓“轻量”就很容易不堪负重。

以 Cursor 的 agent window 为例，我自己的体感是，它和 VS Code 原生窗口的流畅度压根不在一个层级。VS Code 本体的编辑器、侧边栏、命令面板这些核心 UI，是长期打磨出来的。你可以说它是 Electron，但它确实已经优化得非常成熟了。

但 agent window 是另一个东西。

它要渲染长对话、工具调用日志、文件 diff、终端输出、checkpoint、任务状态，还要不断接收流式输出。稍微实现得不够克制，就很容易出现卡顿、延迟、发热，甚至整个编辑器都跟着变沉。

所以我现在越来越觉得，问题不只是“Electron 慢”。

VS Code 自己也是 Electron，但它能做到相当流畅。真正的问题可能是：很多 AI IDE 在 VS Code 之上叠了一个越来越重的 agent 工作台，而这个系统的性能、状态管理和 UI 打磨程度，并没有达到 VS Code 本体那种成熟度。

也就是说，不一定是 VS Code 不行。

可能是上面那层 agent runtime 太重了。

## 再说 Electron

网上很多文章一提 Electron，就喜欢说：一个 Hello World 打包出来都上百 MB，这东西怎么可能轻？

这个说法不能说完全错，但也挺浅的。

我自己也用 Electron 开发过 agent 客户端，所以知道它的问题。体积大、资源占用高、启动成本不低，这些都是事实。

但把所有问题都归咎于 Electron，也有点外行看内行了。

VS Code 基于 Electron，但它并不是那种粗糙的网页套壳。它有多进程架构，有 extension host，有懒加载，有长期性能治理。它真正厉害的地方在于：在 Electron 这个基础上，依然做到了足够轻、足够快、足够稳定。

所以我从来不觉得 VS Code 差。

相反，我觉得 VS Code 可能是 Electron 应用里最值得研究的几个案例之一。

问题在于，VS Code 太成功了。它的插件生态太大，扩展能力太强，历史包袱也越来越重。它几乎什么都能做，反过来也意味着它要兼容各种场景、各种插件、各种语言服务、各种工作流。

强大本身，也会变成包袱。

尤其是 AI 这一波来了之后，很多东西已经不只是“编辑器扩展”了，而是要把一个完整的 agent 系统塞进编辑器。

这就让原来那个轻量的文本编辑器，慢慢变成了一个复杂的工作台。

## 然后我试了 Zed

最近我看到 Zed 发布了 1.0。

1.0 这个版本号对我来说还是有点意义的。不是说它已经完美成熟，也不是说它可以替代 VS Code 的所有场景。但至少它释放了一个信号：这个东西已经进入了一个可以认真尝试、甚至作为主力编辑器使用的阶段。

于是我抱着好奇心试了一下。

结果试完之后，有点回不来了。

坦白讲，我 Mac 底部栏里已经把 VS Code 去掉了，换成了 Zed。

终端里打开项目的方式，也从：

`code .`

换成了：

`zed .`

为什么？

因为它真的快。

VS Code 已经算快了，这点我必须承认。冷启动两三秒，打开项目再稍微等一下，这在一众传统 IDE 面前已经很优秀了。

但 Zed 给我的感觉是另一种状态。

它是那种“点开就开了”的感觉。

冷启动快，打开项目快，切 workspace 快，文件切换也快。我没有做严格 benchmark，也没有拿秒表计时，这些都是体感。但编辑器这种东西，体感其实很重要。

因为你每天都在用。

每天都在打开、切换、搜索、写代码。只要一个工具在这些动作上持续给你一种“没有阻力”的感觉，你很快就会被它惯坏。

Zed 就是这样。

它让我重新感受到了一种很久没见过的轻盈感。

## Zed 的 AI 集成也更舒服

除了快，Zed 另一个让我喜欢的点，是它对 AI agent 的处理方式。

很多 AI IDE 的路线是：我自己魔改一个 VS Code，然后把我的 agent 深度集成进去。

这个方式当然可以做得很强，但也容易让编辑器越来越重。

Zed 的思路看起来更像是：编辑器保持轻，agent 通过协议接进来。

它借助 ACP，可以把外部 agent 接进 Zed 的侧边栏里。比如 Claude Code CLI、Codex CLI、Copilot 这类 agent，只要支持对应协议，就可以作为外部 agent 接入。

这个方向我很喜欢。

因为它不是每家都重新造一个“AI IDE 壳”，而是把编辑器和 agent 解耦。

编辑器就是编辑器。

Agent 就是 agent。

二者通过协议协作。

当然，不同 agent 的认证、计费、能力支持、上下文处理、工具调用方式都不一样，不可能真的做到所有 agent 都完全无缝。

但至少这个架构方向是我喜欢的。

它不像是把编辑器改造成一个越来越复杂、越来越沉重的 AI 工作台，而是让编辑器保持自己的边界，再通过协议把 agent 接进来。

这个差异非常重要。

AI 很重要，但编辑器本身也很重要。

一个编辑器如果为了 AI，把自己搞得越来越卡、越来越重、越来越不稳定，那我会觉得有点本末倒置。

## 插件生态这块，我反而喜欢它现在的克制

再说插件。

VS Code 的插件生态当然强，这点没人能否认。

但强到一定程度，也会让人害怕。

VS Code 插件市场太大了，背后又是 Node 和 npm 生态。npm 作为全球最大、最活跃的包管理器之一，依赖链复杂，投毒、恶意包、供应链攻击这些事情并不少见。

再加上 VS Code 扩展本身权限很大，能读文件、能发网络请求、能跑外部进程。对于开发者来说，这些能力当然很有用；但从安全角度看，一旦插件出问题，影响面也会非常大。

所以我现在对插件市场越来越谨慎。

不是说 VS Code 没做安全治理。它当然有扫描、封禁、publisher trust 之类的机制。但生态规模太大之后，风险很难完全消掉。

Zed 的插件生态目前还远没有 VS Code 那么大。

这当然是缺点。很多 VS Code 里已经成熟的插件，在 Zed 里可能没有；很多细碎的工作流，也不一定能立刻迁移过去。

但另一方面，它也让我觉得更克制。

Zed 的扩展机制和 VS Code 不太一样。它的扩展通常以 Git 仓库形式存在，通过 `extension.toml` 声明能力。有逻辑的部分一般用 Rust 写，再编译成 WebAssembly。运行时还有 capability system，像执行外部命令、下载文件、安装 npm 包这些能力，都属于可被约束的范围。

这并不代表 Zed 插件就天然安全。

很多语言插件还是要依赖 language server，调试器、MCP server、agent server 也可能是外部二进制程序。只要涉及下载、执行外部工具，供应链风险就仍然存在。

但至少它的边界更清楚。

它不是那种无限开放的“什么插件都可以进来改一切”的感觉，而是更收口、更透明，也更符合我对一个轻量编辑器的期待。

## 我不是说 VS Code 不行了

写到这里，可能有人会觉得我是在唱衰 VS Code。

其实不是。

我到现在依然觉得 VS Code 是非常优秀的编辑器。它轻量、稳定、生态成熟，插件体系强到离谱。对于绝大多数开发者来说，它仍然是最稳妥的选择。

而且 Zed 现在也不是没有问题。

它的插件生态还不够大，有些语言和工具链支持还不如 VS Code 成熟，有些细节也需要时间打磨。如果你高度依赖某些 VS Code 插件，或者团队工作流已经围绕 VS Code 搭起来了，那现在立刻迁移到 Zed，未必是一个无痛选择。

所以我不会说：所有人都应该马上换 Zed。

没必要。

工具这种东西，本质上还是看自己的工作流。

但对我来说，Zed 这次确实击中了几个很核心的点。

快。

轻。

干净。

AI 集成方式更现代。

插件机制更克制。

多 workspace 切换更顺滑。

没有那么多历史包袱。

这些东西加起来，就让我第一次认真考虑：也许我真的可以换一个长期主力编辑器了。

## 最后

我一直觉得，开发工具的体验不是靠参数表堆出来的。

什么启动速度多少毫秒，内存占用多少 MB，插件数量多少个，支持多少语言，这些当然重要，但它们都只是结果的一部分。

真正决定你会不会长期使用一个工具的，往往是一些很细微的体感。

打开项目时有没有阻力。

切换文件时有没有停顿。

写代码时编辑器会不会抢你的注意力。

AI 辅助是让你更轻松，还是让整个 IDE 变得更重。

插件生态是帮你扩展能力，还是让你越来越担心安全和性能。

这些感受堆在一起，最后就会变成一个很简单的判断：

我愿不愿意每天打开它？

以前我的答案是 VS Code。

现在，我的答案开始变成 Zed。

所以这次不是严肃测评，也不是技术布道。

就是一次很普通的迁移体验。

我用了很多年 VS Code，也依然尊重 VS Code。

但现在，我确实已经把 `code .` 换成了 `zed .`。

（完）
